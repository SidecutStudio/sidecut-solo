# Plan slices

Read this when ordering work into independently checkable outcomes.

## Steps

1. Put the riskiest unknown first so a failure changes the plan early.
2. Order remaining outcomes by dependency. Keep the product working after each step.
3. Deliver a thin path across the necessary layers, such as joining a waitlist through its form, endpoint and storage.
4. Split a step that combines unrelated areas or cannot describe its check briefly.
5. Fold uncheckable scaffolding into the outcome that needs it.
6. Name any temporary breakage and the step that repairs it.

A check names the command and expected result, or an observable behavior. For a bug, reproduce failure before the fix.

For example, submit the same email twice and confirm one stored row plus an already-registered message. Avoid vague checks such as works correctly.

## Parallel work

Split work only when steps share neither files nor required results. Define any shared interface before splitting its independent consumers.

Leave function bodies to implementation. Name exact signatures only when requirements or inspected interfaces actually constrain them.
